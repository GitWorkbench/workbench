# Automated tests and coverage

## Run the suite

Use Node 22 and the committed npm lockfile:

```sh
npm ci
npm test
npm run build
```

`npm test` runs the Vitest suite, then the existing feature harness. It does not run TypeScript type checking. Git must be installed and available on PATH.

For focused work:

| Command | Scope |
| --- | --- |
| `npm run test:unit` | Pure logic and main process boundaries |
| `npm run test:renderer` | React components, stores, application navigation |
| `npm run test:integration` | Real Git operations in temporary repositories |
| `npm run test:features` | Existing standalone feature harness |
| `npm run test:watch` | Interactive Vitest watch mode |
| `npm run test:coverage` | Full suite with the strict coverage gate |
| `npm run test:coverage:report` | Summarize the last coverage report and list gaps |

## Coverage target

The target is **100% lines, statements, functions, and branches for every executable file in `src/`**. The gate includes files that have never been imported by a test. Only `.d.ts` declarations and `src/shared/types.ts`, which has no executable code, are excluded. Do not exclude a component, error handler, IPC route, or platform adapter to make the percentage pass.

Run the coverage command to obtain the current measured result; a passing functional suite and a passing coverage gate are separate results. The command exits nonzero whenever any per-file metric is below 100%, and still writes these reports:

- `coverage/index.html`: source annotations and individual uncovered branches.
- `coverage/coverage-summary.json`: machine-readable totals for every file.
- `coverage/coverage-final.json`: statement, function, and branch counters.
- `coverage/lcov.info`: coverage for external tooling.
- `coverage/coverage-gaps.md`: generated by the report command, listing every file below the target.

Unreachable defensive branches should be reviewed before changing their source. Keep useful safety guards; add a reproducible failure or race scenario where possible. Assertions must verify outcomes, state, arguments, and failure behavior rather than merely executing lines.

## Required development workflow

Every feature, fix, and refactor includes regression tests and a coverage check. This is the default for implementation work; it does not require a separate testing request each time.

1. Add tests alongside the code. Exercise the successful workflow, relevant errors, and safety boundaries. For a reported bug, first reproduce it with a failing assertion.
2. Run the affected suites while developing. Use real disposable Git repositories for Git semantics and renderer interaction tests for UI behavior; mock external/native boundaries deterministically.
3. Run `npm run test:coverage`, followed by `npm run test:coverage:report`, against the final source. Review the per-file results and annotated uncovered statements, functions, and branches for every changed executable file. Add meaningful cases for missing behavior and rerun the checks.
4. Keep all four 100% per-file thresholds intact. Do not hide executable files, add coverage-ignore directives, weaken assertions, or remove useful guards to pass the gate.
5. Report the exact commands, pass/fail results, measured percentages, and any remaining gaps. Do not describe a passing functional suite as complete coverage. A failed gate remains a failed gate even when functional tests pass.

An explicit request to skip validation applies to that task only and must be reported. Documentation-only changes do not require runtime tests. Type checking and native platform smoke checks are separate from coverage and must be reported independently when performed.

## What the suites exercise

| Area | Examples |
| --- | --- |
| Git repository workflows | Status, staging files/hunks/lines, untracked patches, commits, branches, remotes, stash inspection and selective apply, tags, submodules, worktrees |
| History and recovery | Rebase, split commits, stacked branches, reflog recovery, restore points, rewrite comparisons, bisect, Git Flow |
| Conflict resolution | Three index stages, text/binary/symlink/submodule conflicts, incomplete markers, stale snapshots, manual editing, CodeMirror integration, remembered resolutions |
| Hosting providers | GitHub/GitLab/Bitbucket/Gitea context, scoped server connections, credential storage, sign-in device flow, review files/comments/checks, request creation/retargeting, review worktrees |
| Repository size features | Sparse checkout preview and restore, ignored-file protection, LFS configuration, bounded transfers and cancellation |
| Main process | Electron lifecycle, window commands, updater states/errors, preload contract, IPC argument routing, mutation serialization, process timeouts/output bounds |
| Git Playground | Ten real Git lesson setups and solutions, command grammar and serialization, editor stale-write checks, incorrect solutions, durable milestones/completion, input/path validation, storage failures, coaching/quizzes, history, drafts, tracker and keyboard navigation |
| Interface | Home dashboard, About/updates, guides, typography/settings, navigation, branch sidebar, graph canvas/hover/context actions, commit details, diffs, command palette, terminal and workflow dialogs |

Renderer tests use jsdom and React Testing Library. Feature components normally keep their real rendering and interaction logic while mocking the Electron API boundary. The conflict editor suites use actual CodeMirror with DOM geometry shims. App orchestration tests replace child workspaces to isolate startup, shortcuts, and navigation.

Provider, AI, updater, and process boundary tests use deterministic responses. They never sign in to a real account, use personal credentials, download an update, or contact a real Git remote. Git integration tests use real Git with temporary local repositories and local bare remotes.

Filesystem fixtures must use names supported by the host. POSIX runs retain literal tabs, `>` and `*`; Windows runs use Unicode, spaces and bracket glob characters. Boundary tests exercise the exact tab, ASCII-arrow and wildcard strings on every platform without creating invalid Windows paths. Both fixture variants retain the same data-preservation assertions.

## Test isolation

`tests/setup.ts` and the standalone harness share `scripts/test-git-environment.cjs`. It disables system/global Git configuration, credential prompts, hooks, and signing, and clears inherited repository/index/object paths so a test cannot accidentally target a developer's repository. Fixtures set their own Git identity. Repositories and test configuration are created under the OS temporary directory and removed by teardown. Avoid copying a developer's Git environment wholesale into a simple-git client; the bounded argument-only process adapter provides environment overrides for shadow indexes and worktrees.

Tests that simulate operating systems restore `process.platform` after each case. Unit simulations do not replace native verification of installers, unsigned macOS Gatekeeper prompts, OS permissions, keychain access, terminal availability, and installing a real update. The GitHub Actions matrix runs the suite and production build on Linux, macOS, and Windows; local results only establish behavior on the host where they ran.

## Continuous integration

`.github/workflows/tests.yml` runs tests and the production build for pushes to `main` and `codex/**`, pull requests, and manual dispatches. The separate Linux coverage job enforces all four 100% per-file thresholds and uploads the report even when the gate fails. Both functional validation and the strict coverage job must pass before releasing.

For a regression, add a failing test for the observed behavior, fix the implementation, rerun the affected suite, then run the complete suite and coverage report. Use a temporary repository for destructive Git scenarios. Never run a reset, clean, rebase, merge, or install against the working project as part of a test.
